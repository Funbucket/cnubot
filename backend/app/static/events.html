사용자 이벤트 수집

어디서 수집하고, 어떻게 연결하며, 어떤 형태로 저장하는지 확인합니다.

현재 코드 기준의 설계 안내입니다. 아래 JSON은 가상 데이터이며 실시간 로그가 아닙니다. 저장소는 PostgreSQL의 user_events 테이블이고, 이벤트별 추가 정보는 properties JSONB에 저장됩니다.

수집 흐름

01 · 요청

카카오 스킬 호출

사용자 ID와 버튼 extra를 읽습니다. 학식 조회·기획전 진입 요청이 출발점입니다.

02 · 응답 생성

조회·노출 기록

메뉴 조회, 진입 버튼, 상품 카드 노출을 서버에서 기록합니다.

03 · 구매 버튼

추적 링크 경유

서명·만료 검증 → 클릭 저장 → 외부 상품 페이지로 302 이동합니다.

04 · 저장·활용

user_events

인사이트·실험 분석에 사용하고, 카테고리 클릭은 개인화 선호도에도 반영합니다.

현재 수집하는 주요 이벤트

이벤트기록 시점해석
menu_view학식 조회 처리식당·날짜·인라인 상품 카드 포함 여부
promotion_entry_exposure학식 응답에서 진입 버튼 발견버튼 ID·문구·기획전·노출 경로
promotion_entry_click기획전 스킬 호출extra로 유입 경로 판별. 정보가 없으면 unknown
promotion_exposure상품 노출 기록 함수 호출상품별 1건. 학식 인라인 카드는 응답에 실제 포함됐는지 확인
commerce_card_click유효한 추적 링크 접근상품·버튼 문구·카드 위치·유입 경로
recommendation_click같은 클릭의 추천 서비스 처리상품 ID가 있을 때 추가 기록. 카테고리 선호도 갱신에 사용

한 번의 구매 버튼 클릭에 commerce_card_click과 recommendation_click이 함께 생길 수 있습니다. 두 이벤트를 더하면 클릭 수가 중복됩니다.

저장되는 JSON 형태

DB 행을 JSON으로 표현한 예시입니다. 모든 이벤트가 모든 필드를 채우지는 않으며, properties는 경로에 따라 달라집니다.



필드와 연결 방식
필드의미와 현재 동작


id / event_id / schema_versionDB 순번 / 이벤트 UUID / 기본 버전 1. event_id에는 부분 UNIQUE 인덱스가 있습니다.


user_id / anonymous_iduser_id는 카카오 요청의 사용자 ID입니다. anonymous_id는 스키마에 있지만 현재 주요 수집 함수에서 채우지 않습니다.


request_id일부 응답의 상품 노출과 해당 링크 클릭을 묶습니다. 모든 요청에 자동 부여되는 세션 ID는 아닙니다. 기획전 진입은 새 UUID를 생성하므로 이전 버튼 노출과 항상 일치하지 않습니다.


source / surface유입 경로와 노출·클릭 위치입니다. 수집 함수별로 채우는 방식이 달라 null일 수 있고, properties에도 관련 정보가 들어갑니다.


product_key / taca_item_id내부 상품 키 / 외부 상품 ID입니다. 메뉴·버튼 이벤트에서는 비어 있을 수 있습니다.


experiment_id / experiment_key / variant_key실험 기록 함수가 실험·사용자 배정을 조회해 채웁니다. 일반 퍼널 이벤트는 기본 null이며 실험 배정이 자동 결합되지 않습니다.


properties / created_at이벤트별 JSONB / DB의 TIMESTAMPTZ 기록 시각. 예시 시각은 UTC입니다.




데이터를 읽을 때 알아둘 점
  • 노출은 서버의 응답 생성 기준입니다. 사용자 화면의 실제 렌더링·열람을 확인하는 클라이언트 신호는 아닙니다.
  • 외부 상품 페이지로 이동한 이후의 구매 완료·결제 금액은 이 수집 경로에서 확인하지 않습니다.
  • 클릭 링크를 다시 열면 새 UUID로 추가 기록됩니다. UUID의 유일성만으로 동일 행동의 재시도를 제거하지는 않습니다.
  • 사용자 ID가 없으면 상품 노출·추천 클릭 기록은 생략됩니다. 일반 퍼널 함수는 사용자 ID가 null인 행도 기록할 수 있습니다.
  • DB 미초기화 시 일부 기록 함수는 반환하고, 호출부는 기록 오류를 로그에 남기고 응답을 계속하는 구조입니다. 전송 큐·재시도 보장은 없습니다.
  • 인사이트의 진입형 퍼널은 사용자와 시간 순서로 단계를 연결합니다. request_id로 완전히 격리된 세션 퍼널과는 다릅니다.
