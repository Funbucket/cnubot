# 인사이트 워크스페이스

현재 화면은 `apps/insights`의 Next.js 앱에서 제공한다. FastAPI의 예전 HTML 인사이트·관리 화면 렌더러와 중복 정적 파일은 제거했으며, 이전 관리자 주소는 인증 후 비공개 설정 `ADMIN_WEB_ORIGIN`의 새 웹으로 연결한다. 집계·개인 원자료·JSON 관리 API·카카오 스킬은 기존 백엔드에 유지한다. 관리 폼과 JavaScript는 Next.js의 `templates/admin` 소유이며 React 전체 재작성과는 구분한다. 검증과 설정은 [관리자 웹 앱 문서](../apps/insights/README.md)를 따른다. 아래 과거 배포 기록의 FastAPI HTML 주소는 이전 구조를 설명한다.

## Next.js 인사이트

React 기반 관리자 앱은 [`apps/insights`](../apps/insights/README.md)에 있다. 화면·기간·차트·상품 탐색은 Next.js에서, 집계는 기존 FastAPI 서비스에서 처리한다. 기존 집계 정의는 유지하며 중복 HTML 화면은 제거했다. 새 화면 주소 예시는 `https://example.com/insights/overview`다. 개발·배포·비공개 설정·검증 방법은 앱 README를 따른다.

공통 메뉴는 인사이트·상품/버튼 관리·실험실·이벤트 수집·맛집 관리로 구성한다. 관리 화면은 Vercel의 `/admin/recommendations`, `/admin/experiments`, `/admin/events`, `/admin/restaurants`에서 기존 폼과 운영 동작을 유지하며 공통 디자인으로 제공한다. 이 관리 화면까지 React로 전면 재작성한 것은 아니다. 관리 API는 `POST /admin/workspace/relay`로 암호화해 연결하며 기존 관리자 인증과 편집 헤더를 백엔드에서 다시 검사한다. 허용 경로·동일 origin·JSON 크기 검사를 적용하고, 쓰기 UUID의 영속 기록으로 재전송을 막는다. 읽기 전용 보고서 relay의 권한은 확대하지 않는다.

2026-10-23 관리자 연결의 백엔드 보안 테스트 6개와 프런트 관리자 테스트 6개를 통과했다. 실제 Vercel 운영 후보에서 1440·390·320px의 메뉴 왕복, 상품 설정 초안 변경·복구, 상품·맛집 미리보기, 이벤트 JSON 예시, 직접 주소 새로고침을 확인했다. 기본 실험 어드민의 1440·390px 공통 목록·모든 상세 탭·직접 새로고침 검증과 기존 인사이트 7개 보고서의 회귀 검증도 통과했다. 한글 글꼴은 인사이트와 동일하게 적용해 화면 이미지로 확인했다. 검증 중 상품 설정을 저장하거나 실험 운영 상태를 변경하지 않았고, 배포 전후 실험 상태·계획·시작 시각·고정 정책 무결성을 확인했다. 고정 주소로는 검증한 운영 빌드를 승격한다.

웹 앱의 시각·조작 규칙은 Statsig 공식 콘솔을 참고해 통일했다. 흰 패널·회색 배경·파란 선택 상태, 공통 아이콘, 같은 위치의 기간 필터, 지표별 차트/표 전환을 사용한다. KPI 값은 파란색으로 통일하고 증감은 초록/빨강으로 구분한다. 표의 단위·미측정 값과 기존 집계 정의는 유지하며 모바일 탐색에는 현재 보고서가 보이도록 표시한다. 이 화면 변경은 실험 정책·상태·분석 규칙을 변경하지 않는다.

백엔드의 인증된 `GET /admin/insights/api/{report}`는 `overview`, `fortune`, `restaurants`, `shuttle`, `products`, `quality`, `revenue`, `fortune-users`의 JSON을 반환한다. 기본 기간은 최근 7일이며 `start_date`, `end_date`, `all_time`, `refresh`를 사용한다. `all_time`과 날짜를 함께 지정하거나 날짜 순서가 뒤집히면 거부한다. 응답에는 보고서명·기간·KST 시간대·요청 시각·데이터가 있다. 비교·코호트·계측 누락의 의미는 기존 보고서와 같다.

Vercel은 관리자가 인증된 요청에 대해서만 `POST /admin/insights/relay`를 호출한다. 전용 키의 AES-256-GCM으로 요청·응답을 모두 암호화하며 관리자 비밀번호를 백엔드에 전달하지 않는다. 원자료는 사용자가 펼칠 때 별도 조회하고 집계 캐시에 넣지 않는다. 모든 보고서는 `no-store`이며 브라우저 저장소에 영속 저장하지 않는다. 실제 배포·운영 검증 완료 여부는 배포 작업 결과를 기준으로 확인한다.

2026-10-23 새 JSON·암호화 API 테스트 11개, 프런트 보안 테스트 5개, 타입 검사·프로덕션 빌드를 통과했다. 실제 백엔드에 연결한 프로덕션 빌드로 1440·390·320px의 전체 7개 보고서, API와 표시 수치 일치, 미인증 차단, 차트 전환, 기간 이동·직접 입력 오류 수정·오늘/전체 기간, 직접 주소 새로고침, 원자료 지연 조회, 상품 검색·정렬·최소 노출·CSV, 오류 재시도를 확인했다. 백엔드 적용 전후 고정 정책·실험 상태·계획·시작 시각과 기본 실험 어드민 1440·390px 검증도 통과했다. 이 기록은 Vercel 운영 데이터 연결·배포 후 검증의 완료를 대신하지 않는다.

## 보고서 구성

`/admin/insights`는 기간 선택과 보고서 탐색 화면을 먼저 반환한다. 기간이 없는 기본 진입은 최근 7일이다. 초기 화면 요청에서는 상품 퍼널·반복 노출·개인 원자료 쿼리를 실행하지 않는다.

1. **전체 현황**: 학식·운세·맛집·셔틀·상품의 순사용자, 이전 동기간 비교, 일별 추이와 학식 활동 시간대. 토스 구매확정 수익은 별도 요청으로 채운다.
2. **오늘의 운세**: 신규·재이용 일별 구성, 첫 입력창 이후 등록 완료, 요청 대비 응답 생성, 첫 이용일 코호트의 D1~D7 재이용. 최근 이용자 원자료는 펼칠 때 조회한다.
3. **맛집**: 진입·탐색·추천 순사용자, 추천 응답·빈 결과·재추천, 지도 클릭 사용자·횟수, 일별 추이, 지역·예산·탐색 행동·추천 모드, 식당별 노출·지도 클릭, 탐색 시간대.
4. **셔틀**: 응답 생성 순사용자·조회 횟수, 일별 추이, 운행 중·첫차 전·운행 종료·휴무 상태, 휴무 사유, 요일·시간대.
5. **상품·탐색**: 상품 노출·클릭의 순사용자와 횟수, 카테고리별 클릭 횟수, 경로별 단계 집계, 상품 검색·필터·정렬·CSV.
6. **수익**: 토스의 구매확정·예상 수익과 실 결제금액. 거래처 전체·결제일 기준으로 챗봇 클릭과 직접 연결된 구매 전환율이 아니다.
7. **참여·품질**: 학식 이용 건강성 → 문구별 목록 진입 → 카드 위치별 클릭률 → 반복 노출 반응 → 클릭 위치와 기획전 원자료.

차트마다 단위와 분모를 표시한다. 운세의 신규·재이용은 서로 배타적인 일별 사용자 구성이다. 경로·상품·서비스별 순사용자는 서로 중복될 수 있어 합산하지 않는다. 클릭 횟수는 반복 행동을 포함한다.

## 비교와 재방문

- 이전 기간 비교는 동일 일수이며 오늘이 포함되면 같은 경과시간까지만 비교한다. 이전 기록이 없으면 임의 증감률을 표시하지 않는다.
- 운세 D1은 첫 이용 다음 날, 7일 내 재이용은 이후 7일 중 한 번 이상이다. 코호트 히트맵의 각 D열은 정확히 해당 날짜의 재이용이다.
- 오늘까지 진행 중인 재방문 관찰은 확정으로 처리하지 않는다. 분모가 없으면 `—`, 코호트 미성숙은 `대기`로 표시한다.
- 과거 기간의 마지막 날 D1 계산은 다음 날까지 읽되 선택 기간 밖 날짜를 보고서에 추가하지 않는다.
- 계측 전·측정 불가 값은 차트에서 0으로 만들지 않는다. 날짜 기록이 끊긴 선은 이어 그리지 않는다.
- 문구·배치·반복 노출의 단순 비교는 인과 효과나 무작위 A/B 실험 결과가 아니다.

## 조회와 성능

인증된 관리자용 보고서 경로는 `/admin/insights/overview`, `/admin/insights/restaurants`, `/admin/insights/shuttle`, `/admin/insights/products`, `/admin/insights/quality`, `/admin/insights/fortune?visual=true`, `/admin/insights/revenue`이다. 모두 관리자 인증을 요구하고 응답은 `Cache-Control: no-store`다. 최근 개인 원자료는 `/admin/insights/fortune/users`에서만 별도로 조회하며 집계 캐시에 저장하지 않는다. 기존 운세 경로의 기본 응답은 원자료 호환성을 유지한다.

집계는 최대 48개 키·120초 프로세스 캐시를 사용한다. 분석 제외 사용자 설정도 키에 포함한다. 같은 키의 동시 요청은 하나의 계산을 공유하며 실패를 캐시하지 않는다. 상품·품질 보고서는 같은 집계를 공유한다. 토스 실적의 기존 최대 5분 캐시는 별도다. 새로고침은 현재 보고서의 집계 캐시를 갱신하며 토스 반영 완료를 보장하지 않는다.

상품 쿼리는 다음을 적용한다.

- 관련 프로모션 이벤트와 필요한 열만 세션 임시 테이블로 읽는다.
- 실제 쿼리에 필요한 열의 통계만 수집한다.
- 문구별 사용자·이벤트를 사전 집계하여 반복 DISTINCT 정렬을 줄인다.
- 반복 노출은 모든 노출마다 클릭 전체를 탐색하는 대신 각 반응의 직전 적격 노출을 인덱스로 찾는다. 동일 노출의 여러 반응은 한 번만 센다.
- 재방문은 사용자·날짜 집합을 조인한다.
- 보고서는 repeatable-read 트랜잭션으로 일관된 스냅샷을 사용한다. `work_mem=16MB`는 해당 트랜잭션의 정렬·해시 작업에만 적용되며 연결 기본값은 유지한다.

2026-10-21 운영 데이터에서 측정한 단일 실행 결과는 다음과 같다. 캐시 적중 시간이나 일반적인 성능 보장은 아니다.

| 범위 | 기존 상품 집계 | 최적화 상품 집계 | 독립 전체 현황 집계 |
|---|---:|---:|---:|
| 오늘 | 153ms | 129ms | 24ms |
| 최근 7일 | 1,188ms | 704ms | 128ms |
| 전체 기간 | 14,591ms | 4,203ms | 429ms |

같은 DB 스냅샷에서 경로·반복 노출·배치·문구·기획전·상품·클릭 위치의 집계 결과를 비교한다. 정책 고정 파일, 실험 배정·목표·시작 시각은 변경하지 않는다. 배포 전후 정책 무결성과 기본 실험 어드민을 별도로 검증한다.

## 맛집·셔틀 계측

- 맛집은 기존 `restaurant_events`를 그대로 읽는다. `entry`·`recommendation` 과거 기록도 이용자 집계에 포함하며 지도 클릭만 있는 사용자는 이용자에 더하지 않는다. 한 요청에 여러 이벤트가 생겨도 순사용자는 중복 제거한다.
- 새 `browse` 이벤트는 기존 고정 발화의 진입·지역·예산·별점·랜덤·다른 곳 처리를 기록한다. `005_restaurant_browse_events.sql`은 기존 이벤트를 보존하고 허용 이벤트 종류만 확장한다. 입력 원문과 원본 사용자 ID를 이 테이블에 저장하지 않는다.
- 추천 횟수는 `recommendation`만, 지도 클릭은 `map_click`만 센다. 같은 지도 링크 재접근은 기존 click ID로 중복 제거한다. 지역·예산별 횟수는 조건 선택 횟수가 아닌 추천 응답 기준이다. 랜덤 추천 지역은 실제 추천 식당의 지역이며 예산은 2만원 미만이다.
- 셔틀의 기존 `POST /shuttle/nearby`는 `KakaoRequest`를 받아 응답 생성 뒤 `shuttle_view`를 `user_events`에 저장한다. `feature=shuttle`, 응답 전체 상태, 휴무 사유, 노선별 상태만 추가한다. 여러 노선이 표시돼도 조회 이벤트는 한 번이다. 사용자 키가 없으면 횟수에만 포함한다. 요청 본문은 기존 카카오 형식이어야 한다.
- 맛집 `browse`·셔틀 이벤트는 새 코드 배포 이후부터 수집한다. 과거 누락분을 추정하거나 소급 생성하지 않는다. 카드 노출·응답 생성·지도 열기는 실제 열람·방문·탑승을 보장하지 않는다. 셔틀 외부 링크 클릭은 계측하지 않는다.
- 기간은 KST, 종료일 포함이며 개발자·QA 제외 목록을 적용한다. 맛집은 제외 목록도 SHA-256으로 변환하여 기존 user_hash와 비교한다. 서비스별 사용자는 서로 중복될 수 있어 합산하지 않는다. 집계 응답에는 사용자 식별자를 넣지 않는다.
- 두 상세 보고서는 관리자 인증, no-store 응답, 최대 2분 집계 캐시와 새로고침을 사용한다. 기존 카카오 POST와 발화·버튼을 유지하며 신규 등록은 없다. DB 기록 실패 시 사용자 응답은 계속하지만 재전송은 보장하지 않는다.
