# CNUBOT 학식 상품 묶음 실험 계획 및 어드민 UI·UX 설계

- 작성일: 2026-10-08 KST
- 상태: **설계 v1.0 — P0 기반 구현 완료, 운영 검증·실험 시작 전**
- 이번 작업: 운영 코드 읽기, 기존 통계 분석 검토, 실험 제품 공식 문서 조사, 본 문서 작성만 수행.
- 현재 서비스 상태: 개발자 계정에만 학식 빈자리 3개 상품 미리보기 적용. 정식 무작위 실험은 아직 시작하지 않았다.
- 이 문서의 숫자는 **역사적 관측값 / 계획값 / 화면 예시**로 구분한다. 화면 예시는 실험 결과가 아니다.

- 개발 인계: [구현 범위·API·검증 및 남은 운영 작업](experiment-lab-implementation.md). 아래 역사적 관측값과 시작 승인 항목은 구현만으로 확정되지 않는다. 문서의 “이번 작업/현재는 설계만”은 최초 설계 작성 당시의 기록이다.

## 1. 핵심 제안

**학식 빈자리의 단일 상품 추천을 학생용 3개 상품 묶음으로 바꾸면, 학식 이용을 해치지 않으면서 실제 외부 상품 클릭 사용자를 크게 늘릴 수 있는가?**

이번 실험은 카드 수와 추천 정책을 함께 바꾸는 패키지 실험이다. 미세한 문구 차이를 검증하는 실험이 아니다. 성공하면 패키지 전체를 채택할 근거가 생기지만, 카드 수·가격 제한·카테고리 다양성 중 어느 요소가 효과를 만들었는지는 분리해서 말할 수 없다.

어드민은 매일 다음 세 가지를 바로 알려줘야 한다.

1. **지금 무엇을 해야 하는가?** 모집을 기다릴지, 데이터 문제를 조사할지, 최종 결정을 할지.
2. **효과가 얼마나 큰가?** 사용자 기준 절대 개선, 신뢰구간, 1,000명당 추가 클릭 사용자.
3. **서비스에 해가 없는가?** 학식 이용일 감소, 응답 오류, 지연, 식단 복원 문제.

첫 버전은 현재 FastAPI·PostgreSQL·서버 렌더링 어드민을 확장한다. 외부 실험 SaaS 연동이나 프런트엔드 전면 교체를 전제로 하지 않는다. Statsig 등의 **의사결정 방식과 정보 구조**를 참고한다.

## 2. 사용자 경험과 실험 범위

| 화면 / 조건 | A: 현행 | B: 학생용 묶음 |
|---|---|---|
| 학식 조회 시 기존 상품 출력 슬롯 | 기존 상품 카드 1개 | 한 출력 슬롯 안에 최대 3개 가로 캐러셀 |
| 추천 정책 | 현행 today_deals / food / living 순환 및 기존 유효 후보 | 1만원 이하, 간편식·간식/음료·생활용품 각 1개 목표 |
| 자동 노출 빈도 | 사용자별 KST 하루 최대 1회 | 동일 |
| 학식 본문·식단 탐색·기숙사 아침 복원 | 현행 | 동일 |
| `🔥오늘 특가` 직접 진입 | 기존 최대 6개 | 기존 최대 6개 |
| `🍱자취생 먹을거`·꿀템 직접 진입 | 기존 최대 6개 | 기존 최대 6개 |
| 학교혜택·셔틀 | 현행 | 현행 |

**직접 진입 목록을 3개로 줄이지 않는다.** 실험 상세 화면의 A/B 미리보기에도 이 범위를 상시 표시한다.

B의 상세 정책:

- 표시 상품 가격 10,000원 이하. 배송비가 확인되지 않으면 배송 포함 총액이라고 표현하지 않는다.
- 품절·만료·학생 부적합 카테고리·명백한 대용량을 제외한다. 저장된 유효 제휴 링크와 상품 스냅샷을 사용한다.
- 현재 미리보기의 할인·포장 크기·동일 품목 제외·정렬 규칙을 정식 정책 버전으로 명시하고 시작 전에 고정한다.
- 카테고리별 후보가 부족하면 다른 적격 품목으로 채우고, 그래도 부족하면 2개/1개를 제공한다. 전부 없으면 공통 판정 때 확보한 A 후보로 대체한다.
- B에 배정됐지만 실제 1개를 받은 사람도 B에 남긴다. `planned_variant`, `rendered_policy`, `actual_card_count`, `fallback_reason`을 따로 기록한다.
- 상품의 가격·재고 갱신은 정상 운영으로 허용하되, 선택 규칙·UI·빈도·순위 정책은 실험 중 바꾸지 않는다.

카카오 기존 매핑:

| POST 경로 | 정확한 messageText | 유지할 용도 |
|---|---|---|
| `/promotions/collections/today-deals` | `오늘 특가` | 최대 6개 목록 및 새로고침 |
| `/promotions/collections/food` | `자취생 먹을거 핫딜` | 먹거리 목록 |
| `/promotions/collections/living` | `자취생 꿀템` | 꿀템 목록 |

표시 label과 messageText는 구분한다. 새 동적 발화나 임의 ID가 카카오에서 자동 매핑된다고 가정하지 않는다. 이번 사용자 경험에는 신규 발화 등록이 필요하지 않다. 관리자용 QA 버튼은 인증된 어드민에서 동작하도록 별도 설계한다.

### 3.2 현행 어드민 코드 점검

이번 점검은 실제 화면을 로그인해 조작한 것이 아니라 **운영 서버의 라우터·렌더링 코드·통계 코드를 읽어 확인**한 내용이다.

| 현재 구조 / 동작 | 문제 또는 한계 | 설계 방향 |
|---|---|---|
| `admin_views.py` 실험 생성 폼이 버튼 문구 A/B 중심 | 1개 대 3개 추천 정책을 설명하기 어려움 | 경험·정책·분모·관찰 기간을 포함하는 생성 흐름 |
| `experiments.get_analysis()`가 변형 설정의 단일 product_key로 노출·클릭을 집계 | 여러 상품의 정책 효과와 사용자 ITT를 표현하기 어려움. product_key 누락 시 SQL의 NULL 비교로 집계가 비는 위험 | 배정 사용자 기준 코호트 분석을 새로 정의 |
| 클릭 종류 여러 개를 합친 전환율 | 목록 진입과 외부 이동이 혼재할 수 있음 | 외부 이동 이벤트를 주 지표로 고정 |
| `experiment_stats.compare_proportions()`의 정규근사·Wald CI | 희소 사건·0건 셀에 취약 | Fisher exact + Newcombe-Wilson CI |
| 현행 표본 근사는 귀무 분산에 기준율만 사용하며 target<1 검증도 없음 | 이번 큰 상대 효과에서 그대로 신뢰하기 어려움 | 검정 방법과 채택 규칙까지 포함하는 재현 가능한 시뮬레이션 |
| 실시간 진행률이 가장 큰 군의 노출 수를 기준으로 계산 | 한 군의 증가가 전체 모집 완료처럼 보일 수 있음 | 전체 고유 배정 수와 군별 수, 관찰 완료 수를 별도 표시 |
| `decision_ready`가 유의성까지 포함 | 유의하지 않은 최종 결과는 영원히 판정 준비가 안 된 것처럼 보임 | 판정 가능 여부와 결과 방향을 분리 |
| SRM 데이터 부족이 일부 품질 요약에서 정상 취급 | 미검증과 정상 혼동 | `판단 대기` 상태를 독립 표시 |
| 결과 조회 때 rollup 갱신 | 조회 부하·스냅샷 재현성 문제 | 분석 배치와 읽기 API 분리 |
| 인사이트의 카드별 노출 횟수·피로도 | B의 상품 3건이 노출 기회 3번처럼 보일 수 있음 | 묶음 기회·상품 수·고유 사용자 구분 |

정식 실험의 응답 경로 연결, 성숙 코호트 분석, 안전성 판정은 추가 구현이 필요하다. 현재 사용자 전용 미리보기가 켜져 있다는 이유만으로 실험이 진행 중인 것으로 표시해서는 안 된다.

## 5. 사전등록할 실험 계획

### 5.1 가설과 대상

- 가설: 학생에게 맞는 저가 상품 3개를 같은 학식 슬롯에 제공하면 선택 기회가 늘어, 7일 내 상품 외부 클릭 사용자 비율이 실질적으로 증가한다.
- 대상: 식당 구분 없이 학식 빈자리 상품 노출의 **공통 적격 조건**을 만족한 사용자.
- 배정 단위: 사용자. 동일 사용자는 끝까지 같은 군.
- 배정: 새 실험 키·고정 salt를 사용한 독립 50:50 해시 배정과 영구 저장. 예상 각 1,100명이지만 실제 수가 정확히 같을 필요는 없다.
- 제외: 개발자/QA 계정, 사용자 식별자가 없는 요청, 배정 전에 확정한 운영 테스트 트래픽.
- 동시에 진행할 다른 학식 광고·추천 실험: 같은 사용자 범위에서 금지. 상품 정책 변경 이력도 고정 버전에 연결한다.

공통 적격 조건은 **B 후보 수를 보기 전에** 판단한다: 식별 가능한 사용자, 해당 날짜의 자동 상품 기회 미사용, 광고 출력 위치 존재, 현행 A의 유효 후보 최소 1개. 종료된 기숙사 아침 대체 등 기존 슬롯 조건을 공통 적용한다.

최초 공통 적격 요청의 배정 시각을 `t0`로 저장한다. 최초 응답 실패·B 후보 부족·이후 미방문도 배정 모집단에 남긴다. 실제 상품을 받은 사람만 분석하면 처리 후 선택 편향이 생긴다.

### 5.2 주 지표와 추정 대상

**주 지표: 배정 후 168시간 내 한 번 이상 유효한 상품 외부 클릭이 기록된 사용자 비율.**

```text
Y_i = 1{commerce_card_click 존재, t0 <= event_time < t0 + 168시간}
p_A = A군 클릭 사용자 / A군 전체 배정 사용자
p_B = B군 클릭 사용자 / B군 전체 배정 사용자
주 효과 Δ = p_B - p_A
```

- 최종 분석은 전체 배정자의 관찰 창이 끝난 뒤 수행한다. 관찰 중 사용자에게 0을 넣어 조기 전환율을 계산하지 않는다.
- 중간 참고 수치는 168시간이 끝난 사용자만 사용하고 `중간 참고·최종 판정 불가`로 표시한다.
- 인라인·오늘 특가·먹거리·꿀템의 외부 클릭을 모두 포함한다. 인라인 증가가 목록 클릭 감소로 상쇄되는지도 포함한 정책 효과다.
- 각 사용자는 클릭을 여러 번 해도 주 지표에서는 최대 1명이다. 카드별 CTR·전체 클릭 횟수는 보조 지표다.
- 실험 전 발급 링크의 유효 클릭도 해당 계정의 관찰 창에 있으면 포함한다. 실험 발급 링크만의 효과는 별도 탐색 지표로 제공한다.
- 상품 링크의 계정 귀속은 토큰 발급 계정 기준이다. 실제 링크를 누른 사람의 신원을 확인할 수 있다는 뜻은 아니다.
- 확인된 자동 미리보기·봇·재시도 필터 규칙은 A/A에서 검증하고 시작 전 버전화한다. 원시 수와 필터 후 수를 함께 보존한다. 임의적인 사후 삭제를 하지 않는다.
- 서버가 캐러셀 응답을 반환했다는 기록은 사람이 실제로 보거나 스와이프했다는 증거가 아니다. 지표명은 `응답 포함`을 사용한다.
- 구매·주문·수수료의 사용자 단위 귀속 데이터가 없으므로 **매출 실험으로 표현하지 않는다.** 일별 전체 수수료는 참고 운영 지표일 뿐 A/B 인과 추정에 쓰지 않는다.

### 5.3 검정 및 큰 효과의 채택 기준

| 구분 | 사전 고정값 |
|---|---|
| 주 검정 | 사용자 0/1 결과의 양측 Fisher exact, α=0.05 |
| 효과 CI | Newcombe-Wilson 방식의 두 비율 차이 95% CI |
| 통계적 개선 | Fisher p<0.05 및 Δ>0 |
| 실질적 개선 | 관측 Δ≥+1.0%p, CI 하한>+0.5%p |
| 계획상 목표 효과 | Δ=+2.5%p: 기준 0.7385% → 3.2385% |
| 안전성 | 5.5절의 학식 활동일 비열등성 통과 |
| 최종 채택 | 기간·표본·데이터 품질·효과·안전성 조건 모두 통과 |

Fisher의 exact p값과 Newcombe의 score 기반 CI는 서로 다른 방법이다. 두 결과가 수치적으로 완전히 대응한다고 표시하지 않는다.

+1.0%p는 1,000명당 클릭 사용자 10명 증가, +2.5%p는 25명 증가다. 상대 개선율이 수백 %여도 절대 증분을 먼저 보여준다. 이 채택 한계는 **제안된 사업 기준**이며, 수익 자료로 입증한 손익분기점이 아니다. 시작 승인 시 운영자가 명시적으로 확정한다.

### 5.4 표본 수·검정력·모집 가능성

계획 표본은 **총 2,200명의 독립 배정 사용자**, 예상 군별 1,100명이다. 사용자-날짜·카드·조회 횟수를 표본 수에 합산하지 않는다.

기준율 0.7385%, 각 군 1,100명, IID Bernoulli 100,000회 시뮬레이션의 앞선 결과:

| 실제 B 클릭률 시나리오 | 실제 절대 효과 | 유의성 통과 확률 | 실질적 클릭 채택 조건까지 통과 |
|---|---:|---:|---:|
| 1.50% | +0.7615%p | 약 32% | 약 7% |
| 2.00% | +1.2615%p | 약 67% | 약 33% |
| 2.50% | +1.7615%p | 약 90% | 약 67% |
| 3.00% | +2.2615%p | 약 98% | 약 89% |
| 3.2385% | +2.5000%p | 약 99% | 약 94% |

**이 표는 성공 예측이 아니라, 해당 효과가 실제로 존재한다는 조건에서의 검정력이다.** +2.5%p를 80% 검정력의 정확한 MDE라고 부르지 않는다. `목표 효과`, `지정 검정력의 MDE`, `채택 최소 효과`는 어드민에서 별도 필드로 표시한다.

베이스라인이 0.6~1.3%로 달라지면 +2.5%p에서 실질적 클릭 기준 통과 확률은 약 96~86%였다. 효과 희석·재고 부족·로그 오류를 포함한 예측은 아니다. 안전성 통과 확률을 곱해 확정 성공률처럼 보여주지 않는다.

시작 전 재산출:

1. 현행 정책의 성숙 기준율과 분산, 신규 적격 사용자의 누적 유입 곡선을 갱신한다.
2. 독립 50:50 배정으로 생기는 군별 인원 변동까지 포함한 시뮬레이션을 수행한다. 기존 1,100/1,100 결과는 계획 참고값으로 남긴다.
3. CI 하한·효과 하한·안전성의 공동 채택 확률을 평가하려면 두 결과의 상관을 명시한 추가 시뮬레이션이 필요하다. 현재는 개별 확률만 표시한다.
4. 사전 확정된 계산 코드 버전·seed·반복 횟수·기준율·효과 시나리오를 계획에 저장한다. 확정 전 어드민은 `설계 검증 대기`다.

2,200명은 최근 14일 2,096명 수준에서 경계선이다. 낙관적인 확정 종료 날짜를 제시하지 않는다. 목표 미달이 예상되면 **시작 전에** 더 큰 효과를 겨냥하도록 정책을 개선하거나 모집 계획을 바꾼다.

### 5.5 분산 감소와 학식 안전성

클릭 지표는 사전 클릭 신호가 약하고 다변량 교차검증에서도 분산 감소가 나오지 않았다. **클릭 주 지표에 CUPED/CUPAC 이득을 가정하지 않는다.**

학식 이용일에는 사전 14일 활동일을 공변량으로 사용한다.

```text
G_i = [t0, t0+168시간) 내 학식 조회가 있었던 KST 날짜 수
X_i = [t0-14일, t0) 내 학식 조회가 있었던 KST 날짜 수
G_adj_i = G_i - θ × (X_i - 전체 배정 사용자의 X 평균)
ΔG_adj = mean(G_adj_B) - mean(G_adj_A)
```

- 168시간은 시각에 따라 최대 8개 KST 날짜에 걸친다. UI에 단순히 `7일 중 최대 7일`로 표현하지 않는다.
- θ의 역사적 진단값은 약 0.42026. 현행 성숙 자료로 검증하고 실험 전에 고정한다.
- 신규 사용자·사전 활동 없음은 X=0으로 유지한다. 수집 장애로 인한 미관측과 진짜 활동 없음은 구분하고, 미관측이 있으면 품질 문제로 처리한다.
- 처리 후 노출 수·조회 수·클릭 여부를 보정 공변량으로 넣지 않는다.
- 역사적 분산 감소 41.94%는 앞으로 보장되는 값이 아니다. 실제 보정 전/후 표준오차와 분산비를 표시한다. 실제 감소가 음수여도 0으로 숨기거나 사후 유리한 추정량을 선택하지 않는다.
- Statsig의 CUPED는 사전 행동으로 분산을 줄이는 원칙을 참고했다. CNUBOT의 14일 공변량·고정 θ는 본 데이터에 맞춘 별도 선택이다. [Statsig CUPED](https://docs.statsig.com/experiments/statistical-methods/methodologies/cuped)

**비열등성 한계: -0.20 활동일/사용자/168시간.** 평균 3.468일의 약 5.8%이며 승인할 사업적 허용 손실 제안이다.

- H0: ΔG_adj≤-0.20, H1: ΔG_adj>-0.20.
- 고정 θ로 보정한 사용자 값에 Welch 차이 추정과 t 기반 CI를 사용한다.
- 97.5% 단측 하한이 -0.20일을 초과해야 통과한다. 이는 양측 95% CI의 하한과 같은 임계값이다.
- 각 군 1,100명·실제 손해 없음에서 통과 확률은 분산 감소 40%일 때 약 92%, 감소 없음이면 약 75%다.
- 허용 손실을 -0.15일로 엄격하게 하면 역사적 보정 수준에서도 통과 확률은 약 73%로 낮아진다. 안전 기준과 표본 수의 관계를 함께 보여준다.
- **유의한 악화가 없다는 이유만으로 안전 판정하지 않는다.**

추가 운영 가드레일은 전체 학식 요청 실패율, p95 응답시간, 빈 식단/아침 복원 오류다. A/A에서 기준치를 정하고 운영 중단 임계값을 시작 전에 저장한다. 제안 초기값은 `5분 내 신규 치명 오류 3회` 또는 `최근 15분·군별 100요청 이상에서 B 오류율이 A보다 1%p 이상 높고 실패 5건 이상`이다. 저트래픽에서는 요청 수 부족을 정상으로 표시하지 않고 실제 오류 사례를 점검한다. 이 값들은 운영 경보 기준이며 확증적 통계 검정이 아니다. p95 한계는 카카오 응답 제한과 실제 지연 기준을 확인한 뒤 확정한다.

주 지표 개선과 단일 비열등성 가드레일을 **모두 통과**해야 한다. 보조 지표 중 유리한 하나를 골라 승리로 선언하지 않는다. 탐색 차원은 최초 식당, 사전 활동 수준, 사전 활동 유무 정도로 제한하고 배정 시 값을 고정한다.

### 5.6 일정·중단·확정 규칙

| 단계 | 권장 기간 / 종료 조건 | 허용되는 판단 |
|---|---|---|
| 개발자 QA | 구현 후 시나리오 검증 완료까지 | 화면·링크·식단 복원 확인 |
| Live A/A | 권장 7일, 초기 48~72시간에 기술 점검 | 배정·중복·응답·노출·이벤트 연결 검증 |
| A/B 모집 | 총 2,200명 도달 또는 시작 후 28일 중 먼저 | 모집 진행·품질·운영 장애 판단 |
| 관찰 완료 대기 | 마지막 배정자의 168시간 종료까지 | 기존 배정자에게 원래 군 경험 계속 제공 |
| 집계 확정 | 관찰 종료 + 지연 수집 여유 24시간을 기본 계획값으로 고정 | 완전성 확인 후 최종 분석 |
| 결정 및 적용 | 채택 규칙 판정 + 운영자 결정 | 확대 적용 / 현행 유지 / 미결 기록 |

Live A/A는 별도 실험 키를 쓰고 양쪽 모두 A를 제공한다. A/B 시작 때 새 salt로 재배정한다. A/A에서 p>0.05였다는 것만으로 정상이라고 판단하지 않는다. 기존 48~72시간 안은 기술 smoke test로 두고, 요일 범위를 보려는 권장 기간을 7일로 확장했다. [Statsig A/A 가이드](https://docs.statsig.com/experiments/types/aa-test)

- 2,200명 모집을 종료해도 기존 사용자의 관찰 중 경험을 끄면 안 된다. 새 사용자만 모집을 멈추고 기존 배정자는 자신의 창이 끝날 때까지 군 경험을 유지한다.
- 군별 관측 효과를 보며 기간·표본 목표·배정 비율을 늘리거나 줄이지 않는다. 일반 p값으로 조기 승리를 선언하지 않는다.
- 28일에 목표 미달이면 남은 관찰을 끝내고 `표본 미달·미결`로 마감한다. 관측 결과가 좋다는 이유로 자동 연장하지 않는다.
- 모집 일시중지는 신규 배정만 멈춘다. 기존 경험은 유지하며 28일 상한 시계도 유지한다.
- 긴급 중단은 B 제공을 멈추고 안전한 현행 화면으로 돌린다. 중단 시각·영향 사용자를 기록하고 `운영상 중단`으로 종료한다. 일반적인 최종 정책 효과와 혼동하지 않는다.
- 관찰 창 밖 이벤트는 주 지표에 넣지 않는다. 뒤늦게 도착했지만 event_time은 창 안인 이벤트는 고정된 수집 마감 기준으로 처리한다.
- 데이터 장애를 겪은 사용자를 클릭 0으로 몰래 확정하지 않는다. 복구 불가능하면 `품질 미결`로 결론을 제한한다.

## 6. 어드민 정보 구조

기존 최상위 메뉴를 유지하면서 의미를 명확히 한다.

```text
상품·버튼 관리  |  인사이트  |  실험실  |  이벤트 수집
                                ├─ 실험 목록
                                ├─ 새 실험 설계
                                └─ 실험 상세
                                   ├─ 개요·결정
                                   ├─ 결과
                                   ├─ 데이터 품질
                                   ├─ 경험 미리보기
                                   └─ 설계·변경 이력
```

- **인사이트**: 전체 상품 운영의 기술 통계. 날짜 선택 가능. “이 화면은 A/B 인과 결과가 아닙니다”를 설명 링크로 제공.
- **실험실**: 특정 사전등록 계획의 사용자 코호트·효과·안전성·결정. 임의 날짜 필터가 공식 분석 모집단을 바꾸지 않도록 한다.
- **이벤트 수집**: 운영 진단 상세. 실험의 이상 항목에서 관련 이벤트만 보도록 연결한다.
- 표본 부족·미관측·집계 실패를 모두 `0`으로 바꾸지 않는다.

## 7. 화면별 설계

아래 와이어프레임의 인원·시각·효과는 모두 **디자인용 가상 예시**다.

### 7.1 실험 목록: 상태와 다음 행동

기존의 긴 카드마다 결과를 펼치는 방식보다, 행 단위 목록으로 여러 실험을 비교한다. 진행 중 실험이 하나면 상단에 해당 실험의 요약을 크게 둔다.

```text
실험실                                            [새 실험 설계]

진행 중: 학식 빈자리 — 학생용 상품 3개
[모집 중]  현재 할 일: 관찰 완료를 기다리세요
모집 1,540 / 2,200명     관찰 완료 960 / 1,540명     품질: 확인됨
                                               [실험 확인 →]

검색 [________________]  상태 [전체 ▾]   보관된 실험 [ ]
이름           상태        모집 / 목표    관찰 완료   품질      다음 행동
상품 3개       모집 중     1540 / 2200    960명       정상      현황 보기
이전 실험      미결        820 / 1800     820명       정상      기록 보기
```

목록에는 CTR 경쟁 순위·승리 확률을 넣지 않는다. `관찰 완료`의 분모는 현재 배정자, `모집 진행`의 분모는 계획 목표로 명시한다. 두 막대를 합쳐 하나의 진행률로 만들지 않는다.

### 7.2 상세 개요: 30초 안에 오늘의 행동 판단

```text
실험실 / 학식 빈자리 학생용 상품 3개
[모집 중]  A 50% : B 50%  · 사용자 단위 · 계획 v1

지금은 최종 결론을 내릴 수 없습니다.
남은 모집 660명 / 관찰 중 580명. 데이터 품질 문제는 발견되지 않았습니다.

[모집 1540/2200] [관찰 완료 960/1540] [품질 정상] [운영 오류 경보 없음]
분석 기준: 10/20 09:00 KST   데이터 반영: 10/20 08:55 KST

[개요·결정] [결과] [데이터 품질] [경험 미리보기] [설계·변경 이력]

A 기존 1개                          B 학생용 최대 3개
같은 위치 / 하루 1회                 같은 위치 / 하루 1회
오늘 특가·먹거리·꿀템 직접 진입은 양쪽 모두 최대 6개

채택 조건                         상태
모집 종료·전원 관찰 완료           대기
데이터 품질 검증                  통과
주 지표 유의성·최소 효과           최종 분석 대기
학식 활동일 비열등성               최종 분석 대기

[신규 모집 일시중지] [긴급 중단]    [최종 결정 기록: 아직 사용 불가]
```

주요 상호작용:

- 상단 설명은 하나의 우선 행동만 안내한다. 품질 실패가 있으면 모집 진행보다 앞에 표시한다.
- 모집 목표 도달 예상은 고유 신규 유입 추세로 범위를 제시하고 `예측 불안정`을 허용한다. 28일 상한 도달 가능성이 높으면 그 사실을 보여준다.
- 최종 판정 준비는 유의성과 무관하다. 무효과·미결도 정상적인 최종 결과다.
- `긴급 중단`은 영향 범위와 이유를 짧게 확인한다. 누른 뒤 즉시 멈춤 상태·시각·실제 적용 여부를 보여준다.
- 일반 상태 전환은 명시적 상태 머신을 사용한다. 임의 status 문자열을 보내는 범용 버튼을 제거한다.

### 7.3 결과: 절대 효과와 불확실성을 먼저

```text
결과                         [최종 확정 / 중간 참고] [다운로드]
공식 분석: 전체 배정자, 개인별 168시간 · 분석 v1 · 고정 종료 검정

주 지표                  A                B                차이 B-A
7일 내 상품 클릭 사용자   8 / 1100         35 / 1100         +2.45%p
                         0.73%            3.18%            95% CI [계산값]

1,000명당 추가 클릭 사용자: 약 24.5명 [신뢰구간]
0%p ───── +0.5%p 최소 하한 ─── +1.0%p 채택 관측값 ── ● 효과 ───
                         [지표 정의·계산 보기 →]

학식 안전성              원시 A/B 평균     보정 효과         허용 하한
학식 활동 날짜 수        [계산값]          [계산값·CI]       -0.20일
                         CUPED 사용 / 사전 14일 공변량      [통과/미결/악화]

참고 지표 ▾  인라인 직접 클릭 / 목록 진입 / 전체 클릭 횟수 / 재방문
```

표시 규칙:

- 위의 8명·35명은 와이어프레임 예시이며 실제 결과가 아니다. 구현 시 예시를 운영 데이터 대용으로 넣지 않는다.
- **절대 차이(%p)**가 기본. 상대 변화(%)는 보조 표시이며 A=0이면 `계산 불가`다. 무한대 개선으로 표시하지 않는다.
- 주 지표의 행 색만으로 전체 승리를 표시하지 않는다. 안전성·품질까지 통과해야 상단에 `채택 근거 충족`이 나온다.
- 색상과 아이콘·텍스트를 함께 사용한다. 개선/악화는 지표의 유리한 방향을 반영한다.
- 중간에는 최종 판정 배지를 숨기고 상세 통계에 `고정 종료 검정: 지금의 p값으로 조기 종료하지 마세요`를 표시한다. 기본 개요에는 중간 p값을 올리지 않는다.
- p값은 성공 확률이 아니다. `B가 이길 확률 97%` 같은 문구로 변환하지 않는다.
- 신뢰구간은 0선과 사업 기준선을 함께 보여준다. 범위 밖 잘림은 화살표로 표시하고 실제 숫자를 남긴다.
- 모집 완료 전 `실제 효과 기반 observed power`를 계산해 진행률로 쓰지 않는다. 계획 검정력과 현재 CI 폭을 구분한다.

### 7.4 지표 상세 패널: 숫자를 신뢰할 수 있게

지표 행을 누르면 오른쪽 패널, 모바일에서는 전체 화면으로 연다.

| 영역 | 표시 내용 |
|---|---|
| 정의 | 질문 형태 제목, 계산식, 단위, 높은 값/낮은 값 중 유리한 방향 |
| 분모 | 전체 배정 수, 관찰 완료 수, 제외된 QA 수와 제외 이유 |
| 관찰 창 | 사용자별 t0 기준 168시간, 데이터 마감 시각 |
| 계산 | A/B 분자·분모·원시 평균·차이·CI·검정법 |
| 분산 감소 | 적용 여부, 공변량·θ 버전·커버리지·원시/보정 SE·실제 분산비 |
| 추이 | 모집 날짜별 관찰 완료 코호트, 배정 후 경과일별 탐색 추이 |
| 재현 | 분석 버전·SQL hash·읽기 전용 SQL·집계 파일 다운로드 |

주 결과의 CUPED 버튼은 임의 ON/OFF 설정이 아니라 `공식: 보정` / `참고: 원시` 보기다. 참고 보기를 눌러도 공식 채택 기준은 바뀌지 않는다. 클릭에는 `미적용 — 역사적 예측력 부족`을 설명한다.

차원 분석은 최초 식당·사전 활동 수준 등 사전 고정 차원만 먼저 제공한다. 결과를 탐색해 발견한 하위 그룹에는 `탐색 결과` 배지를 붙이고 전체 결론을 대신하지 못하게 한다.

### 7.5 데이터 품질: 경고에서 원인까지 연결

```text
데이터 품질              마지막 점검 09:00 KST

[통과] 배정 비율          A 772 / B 768 · 기대 50:50 · SRM p=계산값
[통과] 중복 배정          동일 사용자 두 군 배정 0명
[주의] B 묶음 완성률      3개 88% / 2개 8% / 1개 4%
[대기] 응답 오류율 비교   최근 구간의 요청 수 부족
[통과] 데이터 반영        최신 이벤트 5분 전

선택한 문제: B 묶음 완성률
영향: B 경험의 효과가 약해질 수 있습니다. B 배정자를 제외하지 않습니다.
원인별: 생활용품 부족 / 만료 / 품목 중복 / 링크 없음
[영향 구간 보기] [후보 스냅샷 보기] [집계 SQL 보기]
```

필수 진단 계약:

| 진단 | 검사 단위 | 상태 / 처리 |
|---|---|---|
| 배정 SRM | 전체 배정 고유 사용자, 기대 50:50 | p<0.001이면 조사·채택 보류. 부족하면 대기 |
| 군 전환 | experiment_id + user_id | 1명이라도 발견하면 차단 수준 조사 |
| 배정/응답 연결 | 배정→응답 준비→완료/오류 | 군별 손실·지연 비교. 무응답자를 분석에서 제거하지 않음 |
| 묶음/상품 중복 | request_id + bundle_id + position | 같은 요청 재시도 중복 제거, 카드 수와 묶음 수 분리 |
| 자동 노출 빈도 | 사용자·KST 날짜·자동 묶음 | 일일 1회를 초과하면 QA 제외 여부까지 확인 |
| 클릭 귀속 | 발급 토큰·수신 이벤트·계정·시간 창 | 서명 실패, 고아 토큰, 누락을 별도 집계 |
| B 경험 제공 | B의 유효 노출 기회별 actual_card_count | 3개·2개·1개·A대체·실패를 각각 표시 |
| 데이터 신선도 | 이벤트 수신 시각·집계 watermark | 오래된 정상 결과를 현재 정상으로 표시하지 않음 |
| 사전 균형 | t0 이전 활동·클릭·식당 분포 | 탐색 경고. 유리하게 맞추려는 재배정 금지 |
| 미리보기 혼입 | QA 표식 및 제외 계정 | 공식 코호트 포함 0명이어야 함 |

SRM은 배정 비율 검사다. B의 상품 노출 건수가 A의 3배인 것은 SRM이 아니다. 응답 포함 사용자 수의 차이는 전달 품질 문제로 따로 조사한다. 일별·하위 그룹을 반복 검사한 경고를 독립적인 확증적 검정처럼 해석하지 않는다. Eppo도 일반 SRM 반복 검사의 순차 유효성 한계를 명시한다. [Eppo SRM](https://docs.geteppo.com/statistics/sample-ratio-mismatch/)

사전 QA에서 B의 3개 확보율은 **노출 기회 기준 90% 이상**을 출시 준비 목표로 제안한다. 실제 공급 상황으로 확정하고, 미달하면 후보 정책을 실험 시작 전에 조정한다. 운영 중 미달은 효과 희석 진단이지 B 사용자를 제거할 이유가 아니다.

### 7.6 경험 미리보기: 본인 계정 반복 검증

이번에 실제로 겪은 “하루 1회라 다시 볼 수 없음”을 관리자 기능으로 해결한다.

```text
경험 미리보기                       [공식 분석에서 제외됨]
대상: 환경 설정의 개발자 계정        일반 사용자 선택 기능 없음

경험 [A 기존 1개 | B 최대 3개]
상황 [일반 빈자리 | 기숙사 아침 종료 | 후보 2개 | 후보 없음]

[A 응답 미리보기]  [B 응답 미리보기]
[내 다음 학식 조회에서 B 다시 보기]

현재 예약: 다음 적격 조회 1회 / 10분 후 만료
오늘 QA 실행: 3회       [예약 취소]
```

동작 설계:

1. 브라우저 응답 미리보기는 저장된 스냅샷을 읽고 A/B 응답을 나란히 보여준다. 상품 외부 링크에는 `제휴 링크`를 명시한다. 미리보기를 여는 것만으로 클릭을 만들지 않는다.
2. 실기기 검증은 관리자 권한으로 **환경 설정의 개발자 계정**에 일회성 override를 예약한다. 실제 카카오 메시지 전송은 하지 않는다. 사용자가 직접 학식을 조회한다.
3. override는 다음 **적격** 학식 요청에서만 원자적으로 한 번 소비하고, 10분 후 만료한다. 빈자리가 없는 요청에서는 소비하지 않는다.
4. 하루 cap을 우회하더라도 `is_preview=true`, `preview_session_id`로 기록하고 정식 배정·분모·클릭·CUPED·품질 지표에서 제외한다.
5. 과거 운영 노출 기록의 삭제·이벤트명 변경 없이 다시 볼 수 있게 한다. 오늘 수동 초기화 방식은 임시 조치였으며 상시 QA 기능으로 쓰지 않는다.
6. 토큰 발급 시 QA 표식을 서명에 포함해 나중에 클릭해도 분석에 섞이지 않게 한다.
7. 운영자가 미리보기 종료 후 일반 사용자 화면이 동일한지 비교할 수 있도록 `일반 사용자 정책` 요약을 표시한다.

브라우저 미리보기는 카카오 실기기 렌더링의 근사다. 실기기 확인 체크 항목은 가로 넘김, 이미지·가격·제휴 고지, 상품 이동, 더 보기의 기존 6개 목록, 아침 식단 복원이다.

### 7.7 새 실험 설계: 6단계 안내

| 단계 | 입력 / 확인 | 기본값·제약 |
|---|---|---|
| 1. 결정할 문제 | 가설, 기대 임팩트, 정책 책임자 | 주 지표 1개, 작은 문구 실험 예시 제거 |
| 2. A/B 경험 | 위치·카드 수·정책 버전·미리보기 | 같은 위치·빈도, 직접 목록 최대 6개 확인 |
| 3. 대상과 배정 | 공통 적격 조건·제외 계정·단위·비율 | 사용자, 50:50, 새 실험 key |
| 4. 지표·안전성 | 분자·분모·관찰 창·비열등성 한계 | 클릭 168시간, 활동일 CUPED |
| 5. 표본·일정 | 기준율 출처, 효과 시나리오, 최대 기간 | 2,200명은 검증 전 계획값 |
| 6. 검토·고정 | 계측 체크, A/A, 정책 checksum, 채택 규칙 | 누락 항목과 해결 링크 제공 |

비율 입력은 `0.74%`, 효과는 `2.5%p`처럼 사람 단위로 받는다. API 내부 비율 0.0074/0.025 변환은 명확히 처리한다. `0.03`이 3%인지 3%p인지 사용자가 추측하게 하지 않는다.

AI 초안은 보조 도구로 두고, AI가 기준율·분산·표본 수를 근거 없이 채우거나 자동 시작하지 못하게 한다. 관측값은 출처와 기준일을 연결한다.

시작 후 잠기는 항목: 주 지표·관찰 창·분모·배정·정책 버전·표본 목표·기한·θ·채택 기준·중복/자동 클릭 필터. 수정이 필요하면 새 버전/새 실험으로 연결하고 기존 기록을 남긴다.

### 7.8 최종 결정 화면

자동 계산 결과와 운영자 결정을 분리한다.

| 계산 결과 | 설명 | 권장 행동 |
|---|---|---|
| 채택 근거 충족 | 품질·관찰·표본·실질적 개선·안전성 모두 충족 | B 확대 적용 결정 기록 |
| 목표 효과 지지 안 됨 | 충분히 좁은 CI가 목표 +2.5%p를 배제 | 현행 유지, 새 정책 검토 |
| 안전성 미확인 | 활동일 비열등성 미통과 | 전체 적용 보류 |
| 악화 근거 | 효과/안전성에서 해로운 변화 근거 | 현행 유지, 원인 분석 |
| 미결 | 표본 미달 또는 CI가 넓음 | 같은 실험 임의 연장 없이 후속 계획 |
| 품질 미결 | 배정·수집·오염 문제가 해소되지 않음 | 효과 결론 보류, 계측 복구 |
| 운영상 중단 | 장애로 경험을 중단 | 장애 기록과 영향 범위 확정 |

`결정 기록`에는 선택, 근거, 남은 불확실성, 담당자, 시각, 분석 스냅샷 ID를 저장한다. `B 확대 적용`은 결과 열람과 분리된 동작이며 자동 실행하지 않는다. 가드레일을 통과하지 못했다면 좋게 나온 CTR만으로 채택 버튼을 활성화하지 않는다.

### 7.9 공통 디자인·접근성·오류 상태

- 현재 어드민의 기본 색상과 메뉴를 유지한다. 실험 상세는 넓은 본문과 가벼운 탭 구조로 정돈한다.
- 숫자는 tabular digits, 단위는 명시적으로 붙인다. `명 / 건 / 기회 / % / %p / 일 / ms`를 혼용하지 않는다.
- 모바일은 핵심 요약→주 효과→안전성→진단 순서, 큰 표는 고정 첫 열과 가로 스크롤을 제공한다.
- 키보드 탭 이동, 명시적 focus, 텍스트 상태, 색 대비를 제공한다. 툴팁 내용은 클릭·키보드로도 접근한다.
- 로딩은 skeleton, 데이터 없음은 원인과 다음 행동, 오류는 재시도 버튼과 마지막 성공 시각을 표시한다.
- 정상 배지 옆의 데이터 기준 시각을 항상 표시한다. 새로고침 실패 시 기존 값을 보존하되 `오래된 결과`라고 표시한다.
- 정상 운영 상태는 과도한 애니메이션 없이 유지한다. 긴급 경고만 상단에 고정한다.

## 8. 분석·계측·API 설계

### 8.1 이벤트와 식별자의 계약

기존 event table과 배정 table을 활용하되, 추가 스키마는 구현 때 migration으로 확정한다.

| 데이터 | 필수 항목 / 의미 |
|---|---|
| 실험 정의 | experiment_id/key, protocol_version, config_hash, 고정 분석 방법, 상태, 모집 시작/마감 |
| 배정 | experiment_id + user_id unique, variant, assigned_at=t0, pre_covariates, eligibility_version |
| 요청 | request_id, upstream_request_id 가능 시, 수신·완료·오류 시각, route, latency, experiment/variant |
| 묶음 기회 | bundle_id, request_id, user_id, KST 날짜, intended/actual 카드 수, 배치 여부·대체 이유 |
| 상품 응답 포함 | bundle_id + position, product_key, snapshot_id, 가격·정책 버전 |
| 링크 발급/클릭 | token_id, user_id, source_experiment/version/variant, bundle_id, position, event_time, received_at, QA 표식 |
| 분석 실행 | analysis_run_id, 코드·SQL 버전, 데이터 watermark, 모집·성숙 인원, 지표 결과, 진단 결과 |
| 감사 | actor, action, before/after, reason, timestamp; 실제 사용자 ID를 공개 문서에 넣지 않음 |

**실험 전체 ITT 귀속과 링크 출처는 서로 다르다.** 주 지표는 배정 사용자와 시간 창으로 전체 외부 클릭을 조인한다. source_experiment가 없다는 이유로 직접 목록 클릭을 누락하지 않는다. 링크 출처 정보는 진단·보조 분석에 사용한다.

모든 이벤트가 하나의 순차 퍼널을 통과한다고 가정하지 않는다. 직접 목록 클릭도 주 지표에 들어갈 수 있으므로 다음 두 흐름을 따로 표시한다.

```text
실험 전달 품질: 적격 요청 → 배정 → 응답 준비 → 응답 완료 → 상품 포함
정책 결과:     배정 사용자 → 개인별 168시간 동안 전체 상품 외부 클릭 여부
```

카드 3건의 노출 저장을 하루 cap 함수로 각각 호출하지 않는다. 사용자-날짜의 묶음 기회 1개를 원자적으로 확보하고, 상품 1~3건을 같은 트랜잭션으로 기록한다. 현재 미리보기의 묶음 저장 기능을 검토해 재사용하되 정식 실험·QA 메타데이터를 추가한다.

멱등성은 실제 upstream 요청 ID를 우선 사용한다. 없다면 임의 본문 해시만으로 정상적인 같은 발화를 모두 중복으로 간주하지 않는다. 짧은 시간 범위·라우트·사용자 등 정책을 A/A에서 검증한다. 노출 로그 저장 성공과 실제 사람이 본 것을 동일시하지 않는다.

### 8.2 코호트 집계 규칙

- 배정 테이블을 기준으로 LEFT JOIN하여 이벤트가 없는 사용자도 포함한다.
- `event_time >= assigned_at AND event_time < assigned_at + 168시간`을 적용한다.
- 성숙 여부는 서버 현재 시각만이 아니라 이벤트 수집 watermark·집계 마감도 함께 확인한다.
- 분모는 최종 전체 배정 사용자다. 계측 장애는 임의 사용자 제외로 해결하지 않는다.
- QA는 배정 전 대상에서 제외하고, 토큰·이벤트에서도 차단한다. 역사적 개발자 미리보기·cap 초기화 기록을 정식 성과에 섞지 않는다.
- 누적 고유 사용자는 일별 unique의 합이 아니라 코호트 전체에서 다시 중복 제거한다.
- 카드별 노출 피로도는 상품 건수가 아닌 `bundle_id`의 순서로 다시 정의한다.
- KST 날짜는 명시적으로 변환한다. DB 세션 timezone에 따라 달라지는 `created_at::date`에 의존하지 않는다.

### 8.3 제안 API 경계

아래는 **향후 구현안**이다. 현재 제공 중이라고 간주하지 않는다. 모두 기존 관리자 인증·권한 안에서 제공하고 비공개 서버 주소는 문서에 넣지 않는다.

| 목적 | 제안 경로 | 원칙 |
|---|---|---|
| 실험 목록·개요 | `GET /admin/api/experiments` | 마지막 분석 스냅샷 읽기 |
| 상세 결과 | `GET /admin/api/experiments/{id}/results` | run_id·정의·분모·판정 이유 반환 |
| 진단 | `GET /admin/api/experiments/{id}/diagnostics` | 문제→원인→영향→다음 행동 |
| 미리보기 | `POST /admin/api/experiments/{id}/preview` | 운영 집계 부작용 없는 QA 생성 |
| 내 다음 조회 예약 | `POST /admin/api/experiments/{id}/preview-override` | 개발자 계정 고정·횟수/만료 제한 |
| 신규 모집 중지/재개 | `POST /admin/api/experiments/{id}/enrollment` | 기존 배정 경험 유지 |
| 긴급 중단 | `POST /admin/api/experiments/{id}/stop` | 이유·적용 확인·감사 기록 |
| 최종 결정 | `POST /admin/api/experiments/{id}/decision` | 고정 run_id에 귀속 |
| 분석 재계산 요청 | `POST /admin/api/experiments/{id}/analysis-runs` | 비동기 실행·멱등성·진행 상태 |

화면의 30초 polling이 DB 전체 재분석을 일으키지 않도록 한다. 운영 카운터·경보는 짧은 주기, 통계 스냅샷은 기본 시간 단위 배치, 최종은 명시적 확정 run으로 구분한다. 주기는 부하 측정으로 확정하고 UI에 반영 지연을 알려준다.

읽기 API는 상태를 변경하지 않는다. 변경 API는 기존 인증 방식을 고려한 CSRF/Origin 검증·권한 확인과 감사 기록을 포함한다. 프런트에서만 시작 버튼을 막지 말고 서버도 동일한 사전 조건을 검증한다.

### 8.4 판정 상태 모델

```text
lifecycle: draft → qa → aa → enrolling → maturing → analyzed → decided
                              ↕ enrollment_paused
                              └→ stopped

readiness: blocked_quality | waiting_sample | waiting_maturity | ready
outcome:   adopt_evidence | inconclusive | no_target_effect | harm | invalid
operator_decision: null | keep_control | rollout_treatment | plan_followup
```

실험 종료 상태와 효과 방향을 한 필드로 합치지 않는다. `ready`는 최종 판단 자료가 준비됐다는 뜻이며 유의한 개선을 뜻하지 않는다. 표본 미달 마감도 분석 보고서는 생성하되 판정은 `inconclusive`로 기록한다.

## 9. 구현 순서와 완료 기준

현재는 설계만 한다. 추후 구현한다면 UI 장식보다 정확한 분모·계측을 먼저 완성한다.

| 단계 | 범위 | 완료 기준 |
|---|---|---|
| P0-1 | 프로토콜 모델·공통 적격 판정·배정 연결 | 사용자 고정 배정, QA 제외, 직접 목록 최대 6개 유지 |
| P0-2 | 묶음/요청/클릭 계측·성숙 코호트·새 분석 엔진 | 독립 계산과 결과 일치, 0건 셀·관찰 창 경계 검증 |
| P0-3 | 실험 목록·개요·효과표·핵심 진단·본인 QA | 운영자가 재확인·품질 점검·다음 행동을 스스로 수행 |
| P0-4 | A/A·계획 재산출·시작 게이트 | 7일 진단, 최신 기준율·분산·모집 예측, 실기기 QA 완료 |
| P1 | 지표 상세·분산 감소 설명·원인 추적·결정 기록 | 숫자와 결론의 재현·감사 가능 |
| P2 | 탐색 차원·보고서 내보내기·실험 학습 검색 | 공식 결과와 탐색 결과 혼동 방지 |

P0에 포함할 최소 화면은 실험 목록, 단일 실험 개요/결과, 데이터 품질, 경험 미리보기다. 고급 옵션 수십 개를 먼저 만드는 대신 이번 실험을 안전하게 운영할 수 있는 완결된 경로를 만든다.

검증 체크리스트:

- [ ] 같은 사용자 동시 요청·재시도에서도 두 군 배정이나 하루 cap 중복이 없다.
- [ ] 모집 종료 뒤 기존 배정자의 168시간 동안 A/B 경험이 유지된다.
- [ ] B 상품 3개는 묶음 1기회로 기록된다. 상품 2·3번 클릭도 추적된다.
- [ ] B 후보 부족·응답 실패를 포함해 모든 배정자가 ITT에 남는다.
- [ ] 관찰 중 사용자를 실패 0으로 넣지 않는다. t0+168시간 경계와 KST 날짜가 일치한다.
- [ ] 직접 목록에서 최대 6개가 유지되고, 그 클릭도 주 지표에 포함된다.
- [ ] 식단·아침 복원·기존 발화가 실기기에서 정상이다.
- [ ] 개발자 반복 미리보기는 과거 기록 변경 없이 가능하고 결과에 섞이지 않는다.
- [ ] 희소 클릭·한 군 0클릭·양 군 0클릭·로그 장애·빈 코호트에 정직한 상태가 나온다.
- [ ] Fisher·Newcombe·고정 θ Welch 결과를 검증된 독립 계산과 비교한다.
- [ ] SRM 실패·중복 배정·오래된 데이터·누락 입력을 의도적으로 넣으면 시작/채택을 막는다.
- [ ] 전체 배정·군별 배정·관찰 완료·클릭 사용자 수가 SQL 집계와 화면에서 일치한다.
- [ ] 최종 스냅샷과 계획 hash로 보고서를 재현할 수 있다.
- [ ] 키보드·모바일에서 수치·경고·중단·미리보기 동작을 사용할 수 있다.

## 10. 시작 전에 확정할 항목

다음은 구현 중 임의로 숨겨서 결정하지 않고, 계획 검토 화면에서 명시적으로 확정할 값이다.

1. **실질 효과 기준:** 관측 +1.0%p, 하한 +0.5%p, 목표 +2.5%p를 채택할지.
2. **안전성 한계:** 학식 활동일 -0.20일을 허용할지. 더 엄격하면 표본·기간을 다시 계산한다.
3. **현행 정책 재검증:** 2,200명·28일 모집이 가능한지, 최신 기준율·θ·분산이 기존 진단과 얼마나 다른지.
4. **운영 준비 기준:** B 3개 확보율, 오류·지연 경보, 수집 지연 마감, 자동 클릭 필터의 고정값.

본 문서 작성은 위 항목의 승인이나 실험 시작을 뜻하지 않는다. 현재 요청대로 운영 코드·설정·데이터는 변경하지 않는다.
