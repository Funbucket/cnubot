# 카카오 메시지 → POST API 등록 규약

2026-09-11 사용자 확정 사항. 이 문서는 설계 및 수동 카카오 등록의 기준이다.

## 동작

사용자 입력 또는 버튼 messageText → 카카오 관리자에 등록한 발화/블록 → 연결한 POST 스킬 URL → KakaoRequest의 userRequest.utterance 해석 → 카카오 응답 JSON.

API를 구현하는 것과 카카오에 발화를 등록하는 것은 별도 작업이다. 등록은 사용자가 수행한다. 새 API 인계 시 POST 경로, 정확한 발화 목록, 구현 상태를 반드시 제공한다. 등록 시 비공개 운영 설정의 서버 기본 주소에 아래 경로를 붙인다. 이 저장소는 public이므로 실제 운영 IP·호스트·접속 정보는 기록하지 않는다. 전체 URL 예시가 필요하면 `https://example.com`을 사용한다.

## 기존 매핑: 사용자 확인

## 메뉴 빈자리 먹거리 카드

- 빈자리는 food 기획전을 사용한다. 고정 모드는 첫 번째 활성 상품만 선택하고, 해당 상품이 품절·가격/이미지 미확인이면 카드를 생략한다.
- 자동 모드는 API 식품 카테고리와 기존 가격·할인·수량 조건을 적용하고 상세 정보도 재검증한다.
- `특가 바로가기`는 서명된 추적 링크, `먹거리 더 보기`는 food 기획전의 messageText를 사용한다. 기본 발화는 `자취생 먹을거 핫딜`이며 아래 food POST 경로에 매핑한다. 새 발화는 필요 없다.
- 카드가 응답에 실제 포함된 경우만 노출 기록을 남긴다. 노출·상품 클릭에 collection_id, selection_mode, settings_revision을 보관한다. 인사이트는 배포 후 이 정보가 기록된 데이터만 기획전별 집계한다.
- 먹거리 더 보기의 클릭 위치는 카카오 action.clientExtra/action.extra가 전달된 경우에만 구분한다. 누락된 위치를 추정하지 않으며 URL 기반 기획전 정보는 유지한다. 실제 카카오 전달 여부는 운영에서 별도 확인한다.

## 상품 기획전 매핑

| POST 경로 | 카카오에 등록할 정확한 발화 | 용도 |
|---|---|---|
| `/promotions/collections/food` | `자취생 먹을거 핫딜` | 식품·간식·음료 기획전 |
| `/promotions/collections/living` | `자취생 꿀템` | 생활용품과 추천 상품 혼합 기획전 |

두 응답은 서로 상대 기획전으로 이동하는 퀵리플라이를 한 개씩 표시한다. 상품이 정확히 6개인 경우 현재 기획전 발화를 `messageText`로 사용하는 `새로고침` 퀵리플라이를 하나 더 표시한다. `extra.source`는 `promotion_refresh`로 구분하고, 버튼을 누르면 같은 POST 경로가 다시 호출되어 상품을 재조회한다. 상품이 5개 이하인 응답에는 새로고침을 표시하지 않는다. 두 발화 모두 위 표에 이미 등록되어 있어 새 발화는 필요 없다. 학식 메뉴 응답은 두 기획전 퀵리플라이를 `자취생 꿀템`, `자취생 먹을거 핫딜` 순서로 함께 표시한다. 기존 `/promotions/toss-shopping`의 `쇼핑 특가` 발화는 하위 호환용으로 유지한다.

카카오 관리자 등록 시 버튼 `label`과 `messageText`를 구분한다. 위 발화는 서버 설정의 `message_text`와 정확히 일치해야 하며, admin의 문구를 바꾸면 새 발화를 카카오에도 등록해야 한다.

## 학교혜택 매핑

기능별 POST 매핑을 기준으로 구현되어 있다. 사용자의 최종 발화 수정은 구현과 이 문서에 함께 반영한다.

| POST 경로 | 등록할 정확한 메시지 |
|---|---|
| /benefits/home | 학교혜택, 학교 혜택 |
| /benefits/list | 학교혜택 최신, 학교혜택 마감임박, 학교혜택 장학금, 학교혜택 교육, 학교혜택 해외교류, 학교혜택 인턴창업, 학교혜택 교내채용 |
| /benefits/page | 학교혜택 다음 |

학교혜택 접두어로 다른 기능의 발화와 충돌을 피한다. 버튼 label은 '장학금', '다음 5개' 등으로 짧게 표시하되 messageText는 위 등록 문자열과 일치한다.

## 학교혜택 UX 변경에 따른 정리

목록의 `자세히 보기` 버튼은 이제 `webLink`로 공식 공고를 바로 연다. 따라서 새 카카오 블록에는 아래 메시지를 등록하지 않는다.

- `학교혜택 1번` ~ `학교혜택 5번`: `/benefits/detail`로 가던 예전 상세 진입. 현재 목록 버튼에서 사용하지 않는다.
- `학교혜택 이전`: 이전 페이지 버튼을 제공하지 않으며, 현재 구현의 사용자 상태 기반 이전 탐색도 등록하지 않는다.
- `학교혜택 목록`: 번호 상세 화면에서 목록으로 돌아가던 예전 흐름. 직접 공식 공고로 이동하는 현재 흐름에는 필요하지 않다.

기존에 이미 등록했다면 위 메시지는 카카오 관리자에서 삭제하거나 비활성화한다. `/benefits/detail` 엔드포인트는 구버전 말풍선 호환을 위해 당분간 서버에 남겨두지만, 신규 등록 대상이 아니다.

## 상세·페이지 처리 제안

- 고정 발화만으로 사용 가능하도록 사용자별 최근 목록 상태를 DB에 보관한다: 분야, 정렬, 페이지 커서, 노출한 1~5번 공고 ID, 생성/만료 시각.
- /home은 최신 목록 5개를 표시하고 상태를 생성한다. /list는 선택 조건으로 목록 상태를 교체한다.
- /detail은 구버전 말풍선 호환용으로만 최근 목록의 번호를 해석한다. 신규 카드에서는 호출하지 않는다.
- /page는 `학교혜택 다음`에만 사용한다. 이전·목록 상태는 신규 UX에서 제공하지 않는다.
- 상태 만료는 마지막 목록 생성 후 30분으로 제안한다. 없거나 만료되면 최신 목록을 다시 제공하고 재선택을 안내한다. Redis나 메모리에만 저장하지 않아 프로세스 재시작·복수 워커에도 일관성을 유지한다.
- 고정 번호만 쓰면 과거 말풍선의 1번도 가장 최근 목록의 1번으로 해석된다. 화면에 '번호 선택은 가장 최근 목록 기준'을 안내한다. 과거 카드에서도 원래 공고를 보장하려면 검증된 clientExtra 전달 등 별도 설계가 필요하다. 이 한계를 숨기지 않는다.
- 임의 검색어를 붙이는 '학교혜택 검색 토익' 등은 정확한 고정 발화 매핑만으로 지원된다고 가정하지 않는다. 자유 검색은 패턴/엔티티 또는 fallback 연결 설계 후 별도 추가한다.

## 완료 시 인계

구현된 POST 경로와 테스트된 messageText를 위 표에 반영하고 미구현 표시를 제거한다. 응답의 모든 messageText가 등록표에 포함되는지 확인한다. API 테스트와 카카오 관리자 등록 후 실제 메시지 연결 확인을 구분하여 보고한다.
